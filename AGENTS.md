# Not Mario's World — Project Rules and Feature Contract

This file records the agreed requirements for the company's Game Day Thursday game. Read it before changing gameplay, UI, networking, scoring, or assets. It describes the established behavior; it does not authorize unrelated features or balance changes.

## Authority and working rules

- The user is the design and POC authority. Do not silently change gameplay, UX, visual behavior, progression, or game-design constraints. Do not declare the POC successful, failed, or finished on the user's behalf.
- New explicit user instructions take precedence over this document. When an authorized task changes a rule, update this file and the relevant player-facing documentation together.
- Preserve existing features while fixing bugs. Make routine implementation decisions within the authorized scope without repeatedly requesting approval.
- The main agent coordinates requirements, decisions, delegated work, review, and final status. Handle small changes directly. For substantial clear implementation, use a Grunt; for unclear architecture or difficult investigation, use a Planner before implementation. Pass only the needed context, avoid duplicate investigations and unnecessary delegation chains, and tell workers not to revert others' edits.
- Never invoke or switch to GPT-6 Astra automatically. Ask the user for explicit approval first, explaining the unresolved problem, previous attempts, why the other models are insufficient, and the expected contribution. If approved, use medium reasoning or lower.
- Report implementation, verification, and remaining limitations accurately. Distinguish automated coverage from manual browser checks and actual internet/capacity rehearsals.

## Game concept and platform

- An original, playful pixel-art platform race/battle royale for a company event. Collect coins, travel farther, and escape the configured race levels to earn the highest score.
- Desktop browser and keyboard play. Mobile controls are outside the agreed scope.
- Internet multiplayer, deployed as a Node Web Service on Render, with room-code entry and shareable invite links.
- Support a host plus up to **25 players**. The host is an observer/controller and does not consume a player slot.
- Every player runs a separate simulation of the same level layout. Players do not collide, share collectible depletion, or physically enter one another's world. Chest powers, coin-funded targeted attacks, and host-triggered power challenges are the explicitly requested interactions between worlds.
- Layouts and obstacle definitions must be identical for every player. Random power types and quiz questions do not change the terrain. Chest attacks target all eligible opponents; coin-funded attacks target one selected opponent.
- Aim for **5–10 minutes** of casual play across the configured race levels, including surprise deaths. Actual duration depends on skill and needs team rehearsal; do not claim the target has been proven merely because tests pass.
- No particular licensed character or theme is required. Preserve the original artwork and playful surprise-death tone.

## Session and host flow

- The host creates a room, configures it, and **starts the race manually**. Joining or spawning must not start the round.
- Clicking **Host a game** in the homepage header immediately creates a room and opens its host dashboard using the normal authenticated creation flow and default settings. Keep the existing duplicate-click guard and error handling; room creation does not start the race. The separate Host a room tab may still expose the create/resume controls.
- Room states are lobby, running, settling, and ended. Settling stops gameplay and collects final reports for at most two seconds before publishing immutable ranks. Host actions are authenticated separately from player access; a room code must not grant host control.
- Host settings are editable in the lobby. Round duration defaults to **10 minutes** and is configurable from **1–60 minutes**.
- The host can reorder every catalog level in Game settings, including putting ocean first for testing. Every sequence includes each configured race level exactly once. The catalog order is the default (currently forest → ocean); there is no three-level limit. The selected order is room-specific and fixed when a run starts. Late joins and refreshed runs begin at the first world in that selected order, with the shared remaining time.
- Keep biome identity separate from race position. Stage numbers, progress indicators, and the host dashboard follow the selected sequence; artwork, music, chests, checkpoint IDs, and escape broadcasts follow the actual biome. Finish only after the last world in the selected sequence, even if it is the forest or ocean. Do not reorder the global `LEVELS` array to implement this setting.
- Scoring settings default to **10 points per coin** and **1 point per 32-pixel distance tile**; the current supported range for each weight is 0–1000.
- Coin-funded attacks default to **30 coins** and a **60-second per-player cooldown**. The host can configure the cost (1–1000 coins) and cooldown (1–3600 seconds) in lobby Game settings. These are separate from score weights and shared power/quiz durations.
- The host can separately configure **power duration**, **attack-answer window**, and **defense-answer window** in the lobby, each from **1–60 seconds**. Defaults are **5**, **10**, and **10 seconds**, respectively. The server owns these deadlines; quiz progress and result broadcasts must use the configured values.
- The host can also configure every power's strength: Sticky Boots speed (10–90% of normal, default 55%), Wrong Way speed while reversed (50–200%, default 100%), Ice Skates speed (110–250%, default 170%), Ice Skates braking grip (2–50% of normal, default 12%), and Ink Cloud darkness (0–95%, default 95%). Lower ice grip preserves more momentum. The server latches strength when the turn begins; local physics and rendering use those issued values consistently.
- Late arrivals are allowed during a running round. They start the first world in the selected sequence and have only the room's remaining time, with no personal timer extension.
- Refreshing/rejoining a player during an unfinished round resets their run: location, score, banked points, checkpoints, inventory, and collected coins. It is not a saved-game recovery feature.
- A disconnected player must stop moving. Rejoining the same disconnected name replaces that entry; players should use distinct names.
- The host can resume their host session after refresh using the credential in that tab's session storage. This is separate from player-run reset behavior.
- The host can end a running round manually and return an ended room to the lobby for another round. Manual end stops gameplay at the server-issued cutoff and uses the same bounded final-report settlement as natural expiry.
- Post-round arrivals may watch as unranked spectators when room capacity permits. Reconnecting to frozen results must not reset or rerank those results.

## Death, checkpoints, and scoring

- Creature body contact is harmless. Projectile hits, active authored melee attack hits, spikes, bomb/spike decoys, and falls kill instantly. There is no agreed health/damage system. Stomping creatures from above still defeats them and bounces the player.
- In every race level, visible and disguised spikes use a centered collision box at **85% of their visual width and height** (7.5% inset on each edge). Preserve the full-sized artwork and original trap coordinates for death reveals. Bombs, projectiles, and pits keep their existing collision rules.
- Respawns are unlimited and occur after **3 seconds**.
- JSON levels use authored ordered checkpoint triggers and anchors. The legacy inferno course retains checkpoints at **25%, 50%, and 75%**. The exit completes/banks the level rather than acting as another checkpoint.
- JSON spawn and checkpoint banners default to a midpoint foot anchor `[0.5, 0.5]`, placing the player's feet at the banner's center before landing. The live forest's start and both checkpoint anchors use this midpoint; explicit custom anchors remain supported.
- Each new checkpoint saves **respawn location, current points, coin count, collected coin IDs, farthest distance, and progress**.
- Collected coins and their points are protected immediately for the run, before and after checkpoints. Death never restores collected coins or claimed treasure chests. Refresh/rejoin still resets the run.
- Death restores checkpoint distance/progress and respawn position, or resets distance/progress and respawns at the level start before the first checkpoint. Collected coin points and previously banked levels remain safe.
- All collected coins stay collected across death. Claimed reward chests disappear with gold/cyan pixel bursts; coins disappear with gold collection bursts. Decoy chests remain. Never allow coin duplication or repeated-checkpoint score farming.
- Checkpoints advance monotonically. Only a later checkpoint can replace the save; revisiting the same or an earlier checkpoint must not overwrite or downgrade it.
- Unreached flags are blue; **all reached flags remain gold**, including after coordinator messages and respawn. Checkpoint state is local and never waits for server confirmation.
- Checkpoints must have solid support and clear landing/respawn space. Touching a flag from ground level must not kill the player. Do not allow nearby hazard placement or enemy patrols to invalidate its safe landing area.
- Respawn resets enemy and moving-platform cycles. The saved scoring/collection state and separately tracked power inventory must still survive as specified.
- Current total score is `banked + current coin points + floor(farthest current-level distance / 32) * distancePoints`.
- Distance uses the farthest point reached, so walking backward and forward cannot farm points.
- Completing a level banks its full current score **once**, including checkpoint-protected points, then starts the next level with a fresh checkpoint state. Death in a later level never removes earlier banked points.
- On reaching an exit, stop the background loop and play that biome's complete victory stinger once. Hold the player safely in the cleared biome until the stinger ends before entering the next selected world. Bank score and announce the escape immediately; final-course completion time remains the exit-contact time. The shared clock continues, and round expiry/manual end takes precedence over the cue. Muted, hidden, or unavailable audio uses the cue's duration without blocking progression indefinitely.
- Completing the last world in the selected sequence banks the final level and waits for the shared room timer and ceremony; it does not immediately end the round for everyone.
- At time expiry, include **banked points plus current unbanked points** in the final result.
- Highest score wins. Ties favor earlier full-course completion measured from the **room's start**, then join order for remaining ties. An unfinished player has no completion time.
- Freeze final scores and ranks at round end. Disconnects, refreshes, reconnects, and new spectators must not change podium placements.

## Critters and projectiles

- Authored creatures have **idle, moving, player detected, attack, dead** animation slots; the attack slot is optional for compatibility. Shooters retain **idle, shooting, player detected, dead**. The fired projectile is a separate animated definition with a flight sequence and optional impact sequence. Preserve the original animation names/frames and map these slots explicitly; imported hurt/lunge/slam/dive artwork does not authorize extra movement or combat abilities.
- Character import includes manifest projectile definitions, resolves stable shooter/projectile references, and retains existing atlas/cut/placement identities. Missing detected/dead artwork stays unassigned rather than being fabricated. Runtime state selection is automatic in the JSON viewer and live game; editor preview selection remains temporary.
- The editor's **Ranges** overlay shows selected actors' effective detection distance and vertical player-foot limit, including placement overrides. Creature detection requires the player's support to belong to the creature's current connected support chain. Range visibility is temporary editor state and must not alter exported levels or live gameplay.
- Non-damaging player-detected artwork plays once when detection begins, before chasing/shooting, and replays only after detection is lost and acquired again. Preserve existing platform support/chase and stomp behavior. Creature bodies never kill on contact: melee damage uses the mapped attack animation's explicit `damage_active_indices` and authored hazard shapes/hitbox, independently of the body collider used for stomps. Missing or empty damage windows are harmless. Legacy creatures without authored melee attacks retain only their configured projectile attacks. Shooter spawn offsets are normalized deltas from the authored visual pivot, transformed with the actor. Fire at the selected shooting-animation frame once per cycle; keep fired projectiles ephemeral and local, with no placement/document mutation or network payload expansion.
- The sequence editor exposes an explicit Damage active control for each ordered frame. The user chooses damaging frames and draws the separate Damage hitbox; never infer either from animation names or body geometry. Reordering/removing frames preserves the damage events on the corresponding frame occurrences, and an explicitly empty damage window stays harmless. Editing these controls does not automatically replace production JSON.
- Creatures repeat a one-shot melee attack while the player remains detected and within configurable `attackRange` (horizontal body-edge gap, default 64 pixels), with `attackCooldownMs` (default 1500 ms) after each completed attack. Facing locks and movement pauses for the attack animation; wind-up, active frames and recovery follow the authored sequence. A dedicated `states.attack` mapping takes precedence. For older exports, a mapped player-detected sequence with explicitly marked damage frames can serve as the attack sequence at close range instead of firing at the initial detection distance. Detection artwork without marked damage frames remains a one-time cue. Death/respawn resets combat cycles.
- Creature **Lethal attacks** is the melee enable/disable control. Actual damage still requires the separate authored damage region and explicit active frames; enabling it never makes the body collider lethal. Explicitly authoring damage geometry or enabling a Damage active frame also enables attack lethality. Ordinary hazard/projectile behavior is unchanged.
- Player respawn/restart resets actor states, patrol cycles, shooting cooldowns and fired projectiles while preserving the established checkpoint/coin and coordinator-owned inventory rules. Dead actors stop dealing attack damage, play their mapped death sequence once, and then disappear. Authored source levels are only changed when the user places/exports actors.
- Shooters without an authored spawn offset fire from the forward visual edge at half height, avoiding the foot pivot inside supporting terrain. Explicit pivot-relative spawn offsets remain authoritative and use the same values in the editor and runtime.
- Selected shooters show an editor-only cyan projectile-spawn crosshair connected to their visual pivot. Its position uses the same transform and effective offsets as fired projectiles, updates when offsets change, and remains visible independently of the Ranges toggle.

- Critters live on both ground and raised platforms. A placement can select multiple supporting platforms through `supportIds`; legacy `supportId` remains supported. An explicitly present array overrides the old singleton; an empty array returns to automatic support inference. The editor offers a canvas picker that toggles platforms while preserving the creature selection, highlights chosen supports, and supports Done/Escape, removing entries and automatic support. Changes use normal undo/autosave/export.
- Patrol and chase stay within the current connected run of selected, visible solid support surfaces. Join only seams of at most 8 pixels with surface-height differences of at most 8 pixels; never bridge real gaps or stacked platforms through a combined bounding box. Moving and vanishing support can split the run; use the actual support under the creature for platform carrying. Chase only while the player stands on that connected run, not merely nearby or at a similar height. Resume patrol when the player leaves it.
- Maintain patrol movement independently of chase direction. Critters must not camp at the left edge and make landing jumps routinely unavoidable deaths.
- Keep the entire critter supported by its platform chain, allowing only the bounded tile seams above; do not let it float past cliff edges.
- Creature flight is an explicit `behavior.flying` boolean, configurable through **Flying creature** in shared runtime behavior or placement overrides. It defaults off and is not inferred from `physics.gravity`, artwork or names. Flying creatures remain alive and visible when their current platform vanishes, retaining their last connected patrol path and altitude instead of teleporting to another support. Ground creatures keep their existing support-loss behavior. This does not grant new cross-platform detection, chase or attack abilities; respawn/restart resets the cached path.
- Some critters telegraph and fire aimed, lethal projectiles.
- Shooters aim at the center of the player's head (upper quarter of the player body) when firing. Authored and legacy shooters share this target calculation; fired projectiles retain their straight trajectory.
- Projectiles are visibly **fire-shaped**, larger, and slower. Current shared tuning is **120 pixels/second**, a **16×16** collision body, a **4.8-second** firing interval, and a **3-second** lifetime. The interval reflects the requested 50% firing-frequency reduction.
- Renderer and simulation must use the same projectile dimensions/tuning so visible flames and collision remain aligned.

## Chests and powers

- Not every chest is a decoy. JSON levels use their authored power/decoy chest roles. The legacy inferno course has **three real power chests** per player; other chests can hide lethal surprises.
- The current JSON forest and tide each use their three authored power chests. Legacy inferno reward chests remain at **3880, 7380, and 10880**. These legacy chests sit after the three checkpoints, with cyan sparkles. Keep rewards distinguishable from decoys, with stable IDs, solid support, and clear access.
- Each chest grants one random power, allowing **up to three uses per level**. Players can hold or reserve **only one power at a time across levels**, without stacking inventory.
- Reaching another chest while holding a power shows an **in-world Attack / Replace choice**. Attack queues the current item and leaves the new chest unopened until the slot is free. Replace discards the current item and claims the new chest; replacement does not grant an extra inventory slot.
- Cache an unopened chest's offered reward for that run so walking away and returning cannot reroll it. The browser detects chest contact; the server validates choices against that reported contact, the known chest, offer, held-item identity, current run, reported liveness, and round deadline. The server does not reconstruct collision geometry. A queued item cannot be replaced.
- An unused held power survives death. A claimed chest stays spent across respawns, regardless of when a checkpoint was reached. Used powers/chests must never regenerate through death or checkpoint rollback.
- Entering the next level gives access to that level's authored fresh chests and discards an unreserved old-level item. Already queued requests remain tied to their original level/item and survive the transition; a reserved old item blocks new pickup until consumed. An active turn has already consumed its item and is not a second held slot.

## Global power queue and broadcasts

- During a running round, the authenticated host can choose any of the four powers and challenge every eligible connected, spawned, unfinished player, including players currently respawning. The host skips the attacker quiz and consumes no player chest/inventory. - Host challenges share the same FIFO queue with player attacks and escape announcements, configured defense window, latched power strength, and full effect/result duration. Host requests belong to the current round, survive host reconnection, and clear on round end/reset. The host is never a player target.
- Only **one power turn** can run across the entire room at a time, even when players are on different levels. A turn includes its attack quiz, defense phase, and effect/result phase.

## Attack and defense quizzes

- Activating a power requires a random **general-knowledge** question from a server-owned pool. This pool is separate from configurable lobby icebreakers; it currently contains 102 questions, with 50% drawn from Philippines trivia.
- Attacker: the configured attack window (**10 seconds by default**), **one attempt**. Wrong or unanswered means the power applies to the attacker for the configured power duration, without a defender quiz.
- Correct attack: every eligible opponent for a chest attack, or only the chosen opponent for a coin-funded attack, receives a private defense question with the configured defense window (**10 seconds by default**) and **one attempt**.
- Defense happens **before the effect starts**. Correct defense blocks that player's effect; incorrect/unanswered defense leaves that player affected. One player's success must not protect others automatically.
- Resolve early when all applicable answers are in. Otherwise resolve at the authoritative deadline, then give affected players the full configured effect duration.
- Answers are **case-insensitive**. Preserve Unicode normalization, trimming, repeated-whitespace normalization, and the accepted aliases in the server question bank.
- Keep answer keys and accepted aliases on the server. Never expose them in static public files, snapshots, host previews, or client-side validation. Players receive only their own question; the host may view question previews without answer keys.
- Validate the socket's participant, current run, transaction ID, challenge ID, phase, deadline, and one-attempt state on every answer. Reject stale, duplicate, forged, or other players' submissions.
- A targeted defender must get a question even if they have **no held chest power**. A committed queued attacker must still get their attack question after death or level completion.
- Death must not hide an active quiz or make its answer inaccessible. It does not pause the room clock or quiz deadline.
- Show the question, answer input, submit control, and timer **together inside the game viewport**. The actual player uses one DOM card, independent of the canvas animation lifecycle; host previews are read-only.
- Sync the card from server coordinator events, with lifecycle recovery on tab visibility changes, page restoration, resizing, and fullscreen changes. Do not rely solely on `requestAnimationFrame` or periodic full-state snapshots for its existence or visibility.
- Preserve typed input across repeated snapshots of the same challenge; reset for a genuinely new challenge. Submit once, restore controls after a rejected request when appropriate, and prevent duplicate handlers/submissions.
- Help dialogs must not cover an unanswered quiz. Focus the input and suppress gameplay key handling while answering. Restore normal play after submission/closure.
- A bystander or a player who has already answered should not receive a fresh answer input. Explain the phase/target status instead of implying a missing question.
